# 栅格图像场景中的规划算法说明

本文说明 `capability_mission_planner` 如何基于
[`examples/data/image.png`](../examples/data/image.png) 完成地图处理、能力约束任务分配、路径规划、
负载优化和多机器人时空冲突消解。

最终规划结果见：
[`output/capability_mission_plan.png`](../output/capability_mission_plan.png)。

## 1. 完整算法流程

整个过程不是由单一算法完成，而是一个分层规划流程：

```text
像素阈值栅格化
  ↓
BFS 最大连通分量提取
  ↓
机器人和任务点吸附到合法栅格
  ↓
能力集合约束过滤
  ↓
最受约束任务优先排序
  ↓
A* 计算绕障路径代价
  ↓
最便宜插入构造多机器人路线
  ↓
同点任务合并
  ↓
最大负载 + 总负载目标评价
  ↓
单任务重定位局部搜索
  ↓
CBS 高层冲突树 + 低层时空 A*
  ↓
无冲突轨迹验证
  ↓
PNG 结果绘制
```

核心规划算法包括：

- A* 最短路径搜索；
- 带能力约束的最便宜插入；
- 单任务重定位局部搜索；
- CBS（Conflict-Based Search，冲突搜索）。

BFS 主要用于从输入图片中提取有效地图区域，不参与任务分配。

## 2. PNG 栅格化与连通区域提取

输入图像大小为 `335×447` 像素。验证程序按每个 `5×5` 像素块生成一个
规划栅格，因此得到 `67×90` 的 `GridMap`。

每个像素块根据颜色比例分类：

- 白色比例足够高且黑色比例较低：候选自由栅格；
- 黑色墙体、灰色地图外区域及其他区域：障碍栅格。

扫描图中含有零散噪点，不能简单地把每个非白像素都当作墙体。程序使用 BFS
对候选自由栅格进行连通分量分析，只保留最大的连通自由区域。这样可以：

- 去掉地图外部的零散白色区域；
- 过滤扫描产生的孤立噪点；
- 保证机器人和任务点位于同一个可通行空间。

这部分实现在
[`examples/image_map_demo.cpp`](../examples/image_map_demo.cpp) 中。

## 3. 最近可行栅格搜索

机器人起点和任务点最初通过原图上的近似像素坐标指定，例如机器人 `a` 希望
放置在像素坐标 `(75, 370)` 附近。

程序先将像素坐标换算为栅格坐标，再按照曼哈顿距离搜索最近的合法栅格：

```text
distance = |x1 - x2| + |y1 - y2|
```

候选栅格还必须满足：

- 位于最大连通自由区域；
- 没有被其他机器人或任务点占用；
- 周围具有一定净空。

这个过程只是将人工指定的大概位置吸附到合法地图位置，不是最终的路径规划。

## 4. 能力约束过滤

每个机器人都有能力集合，每个任务都有需求集合。机器人能执行任务的条件是：

```text
任务需求集合 ⊆ 机器人能力集合
```

本次场景中的机器人为：

```text
机器人 a：fire、camera
机器人 b：camera、thermal
机器人 c：fire、camera、thermal
```

例如任务 `T8-fire-photo` 同时需要 `fire` 和 `camera`：

```text
a = {fire, camera}            可以执行
b = {camera, thermal}         不可以执行，缺少 fire
c = {fire, camera, thermal}   可以执行
```

能力过滤可以看作在机器人与任务之间建立二部可行关系，并删除所有能力不匹配的
分配边。它不是匈牙利算法，因为这里并非一对一分配：

- 一个机器人可以执行多个任务；
- 一个机器人也可以不执行任务；
- 机器人数量和任务数量可以不同。

## 5. 受约束任务排序

正式分配前，任务按以下规则排序：

1. 可执行该任务的机器人越少，越先分配；
2. 高优先级任务先分配；
3. 服务时间越长，越先分配。

例如任务 `X` 只有机器人 `c` 能执行，而任务 `Y` 可以由 `a`、`b`、`c`
执行，则优先处理 `X`。这可以降低后续出现无机器人可分配的风险。

该策略属于“最受约束优先”启发式，与约束满足问题中的 MRV（Minimum
Remaining Values）思想相似。

## 6. A* 最短路径搜索

任务分配需要比较一个任务交给不同机器人后的真实行驶代价。地图中存在墙体，
因此不能用欧氏距离或直线距离代替实际路径。

A* 为路线中的每一段计算绕障路径：

```text
机器人起点 → 第一个任务点
任务点 → 下一个任务点
最后一个任务点 → 机器人起点（return_home=true 时）
```

A* 的评价函数为：

```text
g(n) = 从起点到节点 n 的实际步数
h(n) = 节点 n 到目标的曼哈顿距离
f(n) = g(n) + h(n)
```

栅格上的移动规则为：

- 可以向上、下、左、右移动；
- 障碍栅格不可进入；
- 每移动一格代价为 1。

- [`src/grid_path_planner.cpp`](../src/grid_path_planner.cpp)

## 7. 最便宜插入启发式

任务归属和任务访问顺序是一起决定的。

假设机器人 `a` 当前路线为：

```text
起点 → A → B → 起点
```

将任务 `C` 分给它时，算法尝试所有插入位置：

```text
起点 → C → A → B → 起点
起点 → A → C → B → 起点
起点 → A → B → C → 起点
```

算法对每台能力匹配的机器人执行同样的尝试，并使用 A* 重新计算每种候选路线的
真实代价，最终选择使全局目标最小的机器人和插入位置。

该问题属于带能力约束的多仓库、多旅行商问题变体。当前实现使用启发式插入，
不是指数复杂度的全局精确求解器。

## 8. 同点任务合并

如果多个任务位于同一个栅格，并且被分配给同一台机器人，例如：

```text
T1-photo 位于 P
T2-fire  位于 P
```

算法将其合并为一个停靠点：

```text
Stop P:
  tasks = {T1, T2}
  service_duration = duration(T1) + duration(T2)
```

机器人只需到达位置 `P` 一次，然后依次执行两个任务。本次规划结果图中的
`1,2` 标记就是一个包含两个任务的共同点位。

## 9. 最大负载与总负载目标

每条机器人路线的负载定义为：

```text
route_load = travel_cost + service_cost
```

整体评价函数为：

```text
score = w_max × max(route_load) + w_total × Σ route_load
```

默认权重为：

```text
w_max   = 1.0
w_total = 0.1
```

其中：

- `max(route_load)` 用于负载均衡，避免一台机器人承担绝大多数工作；
- `Σ route_load` 用于抑制所有机器人的总行驶和服务成本，避免为了绝对均衡而
  制造大量绕路。

本次图像场景的结果为：

```text
机器人 a：travel 54 + service 11 = load 65
机器人 b：travel 130 + service 3 = load 133
机器人 c：travel 120 + service 11 = load 131

maximum_load = 133
total_load   = 329
score        = 133 + 0.1 × 329 = 165.9
```

## 10. 单任务重定位局部搜索

完成初始插入后，算法继续执行局部改进。每次选择一个原子任务并尝试：

```text
从当前路线删除任务
  ↓
插入另一台兼容机器人的任意位置
```

也允许将任务重新插入原机器人路线的其他位置，以改变访问顺序。只有满足以下
条件时才接受新方案：

```text
new_score < current_score
```

算法重复执行，直到找不到更好的单任务移动或达到遍历次数上限。

这是邻域为“单任务 relocation”的爬山式局部搜索。它能修正初始贪心插入的
部分早期决策，但不保证全局最优。例如可能存在单独移动任何一个任务都不能
改善结果、但同时交换两个任务可以改善结果的情况。当前尚未实现双任务交换、
2-opt 或更大的邻域搜索。

## 11. CBS 时空冲突消解

前面的任务分配和路线优化解决：

```text
哪台机器人执行哪些任务，以及按什么顺序访问任务点
```

它们没有解决机器人在什么时刻经过什么位置，因此最后使用 CBS 生成无碰撞的
逐时刻轨迹。

CBS 是一个双层搜索算法。

### 11.1 低层时空 A*

在给定时空约束下，为单台机器人重新规划路径。状态包括：

```text
当前时间
当前位置
已经完成到第几个任务里程碑
```

允许的动作包括：

```text
上、下、左、右、原地等待
```

任务服务时间会被转换为连续的同位置里程碑，因此机器人到达任务点后必须原地
等待足够时间，不能立即离开。

### 11.2 高层冲突树

CBS 高层搜索过程为：

1. 独立计算所有机器人的路径；
2. 查找最早发生的冲突；
3. 为冲突创建两个约束分支；
4. 一个分支限制第一台机器人，另一个分支限制第二台机器人；
5. 分别调用低层 A* 重新规划受影响机器人；
6. 按所有机器人路径代价继续搜索；
7. 重复处理，直到不存在冲突。

CBS 处理两类冲突。

顶点冲突：

```text
同一时刻，两台机器人位于同一个栅格
```

对向边冲突：

```text
t 时刻：机器人 a 位于 X，机器人 b 位于 Y
t+1 时刻：机器人 a 到达 Y，机器人 b 到达 X
```

## 12. 本次任务分配结果

本次设置了 3 台机器人和 8 个原子任务，最终结果为：

| 编号 | 任务 | 所需能力 | 分配机器人 |
|---|---|---|---|
| 1 | `T1-photo` | `camera` | `a` |
| 2 | `T2-fire` | `fire` | `a` |
| 3 | `T3-thermal` | `thermal` | `b` |
| 4 | `T4-photo` | `camera` | `c` |
| 5 | `T5-fire` | `fire` | `c` |
| 6 | `T6-thermal` | `thermal` | `c` |
| 7 | `T7-photo` | `camera` | `c` |
| 8 | `T8-fire-photo` | `fire + camera` | `a` |

对应路线摘要：

```text
机器人 a：3 个任务，2 个停靠点，负载 65
机器人 b：1 个任务，1 个停靠点，负载 133
机器人 c：4 个任务，4 个停靠点，负载 131
```

任务数量少不代表负载一定低。例如机器人 `b` 只执行一个任务，但其任务点距离
起点较远，往返路径较长，因此最终负载为 133。

## 13. 自动结果验证

验证程序不仅输出图片，还检查以下条件：

- 每个任务都已分配；
- 每个任务恰好分配一次；
- 机器人具备所分配任务要求的全部能力；
- 所有任务停靠点均可通行；
- 所有逐时刻轨迹状态均可通行；
- 不存在顶点冲突；
- 不存在对向边冲突；
- 每台机器人都生成了完整的路线和时间表。

只有全部检查通过，结果 PNG 才会显示：

```text
PASS: assignment, paths and CBS conflicts
```

## 14. 复现方法

```bash
cd /home/jazzy/cpp/capability_mission_planner
cmake -S . -B build-image -DCMAKE_BUILD_TYPE=Release
cmake --build build-image --parallel
ctest --test-dir build-image --output-on-failure

./build-image/image_map_demo \
  examples/data/image.png \
  output/capability_mission_plan.png
```

图像读取、栅格转换和结果绘制依赖系统 OpenCV；核心规划库本身不依赖 OpenCV。
