# 多机路径规划冲突解决说明

本文说明离线多机路径规划如何发现和解决时空冲突，以及执行阶段的实时资源预约如何配合工作。

## 总体流程

系统采用“先分别规划路径，再协调时间”的方式：

```text
为每台机器人规划独立路径
        -> 转换为离散时间帧
        -> 检查机器人之间的冲突
        -> 对冲突生成候选约束
        -> 重新规划受约束的机器人
        -> 直到得到无冲突的时间表
```

第一阶段只考虑地图障碍物、机器人能力、任务顺序和跨地图通道。第二阶段使用
Conflict-Based Search（CBS）协调多台机器人。

例如，两台机器人分别得到以下路径：

```text
机器人 A：起点 -> 1 -> 2 -> 3
机器人 B：起点 -> 3 -> 2 -> 1
```

路径会转换成时间帧。每个时间步机器人要么前进，要么在允许等待的位置停留：

```text
A: t=0 起点, t=1 1, t=2 2, t=3 3
B: t=0 起点, t=1 3, t=2 2, t=3 1
```

## CBS 如何处理冲突

CBS 首先让所有机器人按独立路径同时执行，然后寻找最早发生的冲突。
发现冲突后，CBS 创建多个候选分支。例如 A、B 都想在 `t=2` 到达同一位置时，
会创建两个分支：

```text
分支 1：禁止 A 在 t=2 使用该位置
分支 2：禁止 B 在 t=2 使用该位置
```

每个分支只重新规划受到约束的机器人，并继续检查新的时间表。搜索会优先选择
总代价较低的无冲突分支。常见结果是让其中一台机器人提前或延后，在前一个位置
等待一个或多个时间步。

## 冲突类型

### 顶点冲突

两台机器人在同一时刻占据同一个位置，或者实体外形过近：

```text
t=5:
A: (10,10)
B: (10,10)
```

当前实现不再只比较栅格坐标，而是将位置转换到 ROOT 坐标并计算实际距离。两台
机器人的最小中心距离为：

```text
A 的 footprint 半径
+ B 的 footprint 半径
+ A 的安全余量
+ B 的安全余量
```

例如两个 footprint 半径分别为 `0.5 m` 和 `0.4 m`，安全余量总和为 `0.2 m`，
则中心距离不超过 `1.1 m` 时会被判定为冲突。这样可以发现两个相邻栅格中的实体
机器人碰撞。

### 边冲突和扫掠冲突

最典型的边冲突是两台机器人交换位置：

```text
t=0: A=(1,1), B=(1,2)
t=1: A=(1,2), B=(1,1)
```

系统还会检查一个时间步内部的连续运动。它使用两台机器人在该时间步的起点和
终点，按同步线性运动计算相对距离的最小值。如果两台机器人在同一时刻靠得过近，
即使起点和终点并不相同，也会判定为扫掠冲突。

这里计算的是“同一时刻”的距离，而不是两条几何线段上任意两点的最近距离。比如
A 先经过交叉口、B 稍后才经过交叉口，几何路径虽然相交，但不应仅凭线段相交就
判定为碰撞。

### 共享资源冲突

楼梯、电梯、窄通道、门口和交叉口等区域可以配置成共享资源：

```yaml
planner:
  shared_resources:
    - id: corridor-west
      capacity: 1
      cells:
        - [map_000, 10, 20]
        - [map_000, 11, 20]
```

资源格会被标记为类似 `region:corridor-west` 的资源标识。如果两台机器人在同一
时间片占用相同资源，就会产生资源冲突。CBS 会限制其中一台机器人在该时间片使用
资源，使它等待或延后进入。

资源可以配置进入和离开的缓冲时间。例如资源占用发生在 `t=8`，缓冲为 1 秒时，
实际预约范围会扩展到相邻时间片，避免两台实体机器人紧贴着进入或离开窄通道。

当前版本只支持 `capacity = 1`，即共享资源必须互斥使用。

## 低层重新规划

CBS 给低层路径搜索增加以下约束之一：

- 在指定时间片禁止占据某个位置；
- 在指定时间片禁止使用某个共享资源；
- 在指定时间片禁止执行某条边移动。

低层搜索会在满足约束的前提下重新寻找路径。普通位置可以等待；共享区域也可以
等待，但等待期间仍然占用该资源；边移动和楼梯、电梯等过渡过程不能在中途等待。

## 执行阶段的实时预约

`LiveReservationTable` 是执行层使用的轻量资源预约表，与离线 CBS 相互独立。

例如：

```text
A 预约 door，时间 2 到 5
B 尝试预约 door，时间 5 到 7  -> 拒绝，端点时间相交
B 预约 door，时间 6 到 7  -> 接受
```

当 Nav2 报告 A 已经走到时间 6 时，A 的过期预约会被删除。执行器也可以直接
释放某台机器人的全部预约，或在任务延期后重新申请新的时间段。

离线 CBS 生成的是参考调度；实时预约表负责执行时的资源占用。真实速度变化、
临时障碍物、定位误差和服务耗时变化仍需要执行层和 Nav2 实时处理。

## 导出格式

CBS 内部仍按逐时间片状态进行冲突检测。导出到 `plan.json` 时，正式输出为
`navigation_checkpoints` 和 `traffic_events`；底层逐 tick 状态不作为导航接口：

```json
{"type": "turn", "arrival_tick": 3,
 "map_id": "map_000", "grid": [10, 20]}
```

这只改变序列化体积，不改变 CBS 内部的离散时间冲突判断。

## 当前边界

- 共享资源容量目前必须为 1。
- 每个时间帧只有一个资源标识，多个共享资源重叠覆盖同一栅格时无法表达完整的资源集合。
- 初始位置由输入固定给出；如果机器人一开始就处于不可避免的冲突状态，CBS 无法通过
  回溯到 `t<0` 来解决它。
- 多机协调是离线参考规划，不替代 Nav2 的动态避障和执行阶段重规划。
